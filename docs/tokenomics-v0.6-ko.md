## 0. 적용 범위와 변경 효력

본 개정안은 SHAH CAT을 보안·지갑·운영 기술을 개발하는 독립 프로젝트로 설명하고, 그 기술의 실제 서비스와 SHAH의 경제적 역할을 검증하는 기준을 추가한다. 게임과 캐릭터는 별도 제품·브랜드 영역으로 연결한다.

문서 작성·GitHub 게시·PR 병합은 3인의 경제 정책 채택이나 기존 수혜자의 동의를 대신하지 않는다. 채택 전에는 v0.5가 기존 문서 및 대시보드의 경제 수량 기준이다. v0.5 역시 서면 채택과 실제 잠금·자금 집행의 완료를 증명하지 않는다. 채택된 규정과 실행 증빙이 충돌하면 신규 재량 집행을 보류하고 정정한다.

본 개정안은 총량, 개인별 배분, 배정 목적별 수량, 해제 조건과 기존 게임 보상 한도를 변경하지 않는다. 신규 발행·권한 폐기·토큰 이동·자동 매각·온체인 투표를 지시하지 않는다. 서명·승인 도구의 정책 버전은 계속 v0.5이며, v0.6 채택 후에 구현과 서명 메시지 전환을 별도 검토한다.

## 1. 프로젝트 정체성과 기술의 경계

SHAH CAT은 Solana 기반 SHAH 토큰, 지갑·대시보드·운영 도구, 보안 연구를 개발하는 초기 기술 프로젝트다. 독립 운영은 사업·연구 방향을 뜻한다. 현재 SHAH의 기술 기반은 Solana SPL Token이다. 독자 체인 출시나 SHAH를 네트워크 기본 가스 자산으로 사용하는 구조를 이 문서로 확정하지 않는다.

| 영역 | 제품·연구 목적 | 경제적 연결 원칙 |
| --- | --- | --- |
| 지갑·대시보드 | 공개 자산 조회, 상태 확인, 검증된 운영 흐름 | 선택형 유료 기능의 가치와 비용을 먼저 검증 |
| 운영·Treasury 도구 | 요청·정책 승인·증빙·대조 지원 | 소프트웨어 이용료와 고객별 구축·지원 계약 후보 |
| Four-Way·Guardian·PQC | 권한·복구·무결성·서명 관련 연구 | 검증·감사·배포 전에는 유료 자산 보호 약속에 사용하지 않음 |
| 게임·캐릭터 | 콘텐츠와 사용자 경험 | 독립 운영 예산과 CHURU 경제, 선택형 SHAH 활용 |

Solana 거래의 네트워크 수수료는 fee payer가 SOL로 부담한다. SHAH 서비스 요금은 별도 상업 정책이며, SOL 수수료·계정 생성 비용을 대체한다는 의미가 아니다. 수수료 대납은 실제 구현·예산이 있을 때만 제공한다. [공식 수수료 설명](https://solana.com/docs/core/fees)

## 3. 총량과 배분 — 기존 수량 유지

정책상 기준 총량은 **1,000,000,000 SHAH**다. 현재 Devnet 테스트 공급량과 향후 배포 대상 Mint의 실제 공급·권한은 별도로 확인한다. 기술 개발 진척이나 신규 협업자 참여를 추가 발행 사유로 자동 인정하지 않는다.

| 배정 | 수량 (SHAH) | 비율 | v0.6 집행 검토 방향 |
| --- | ---: | ---: | --- |
| 운영 창립자 2인 | 333,333,334 | 33.3333334% | 기존 개인별 권리와 해제 조건 유지 |
| 초기 전략투자자 박원 | 166,666,666 | 16.6666666% | 기존 개인별 권리와 해제 조건 유지 |
| 유동성 확보 | 150,000,000 | 15% | 실제 상대 자산 예산·풀 조건 승인 후 예치 |
| 게임 및 생태계 보상 | 100,000,000 | 10% | 기존 목적과 게임 시범 한도 유지. 기술 보상으로 자동 전용하지 않음 |

| 커뮤니티 성장 | 50,000,000 | 5% | 사전 승인된 캠페인·문서·교육 성과에 연결 |

| **합계** | **1,000,000,000** | **100%** | 배정 목적 변경은 별도 동의 |

배정은 한도이며 유통·매각·계약 채무 발생을 뜻하지 않는다. 개발비의 현금 지급과 SHAH 지급은 별도 승인하고, 같은 성과에 두 예산에서 중복 지급하지 않는다. 외부 감사 비용은 감사인의 실제 견적·수락 통화·독립성을 확인한다. SHAH 보유량을 감사비 현금 확보로 계산하지 않는다.

협업자가 늘면 기존 개발·운영 또는 해당 목적 예산 안에서 검수 기반 계약을 먼저 검토한다. 인원수에 비례해 창립자 몫을 새로 부여하거나 기존 개인 배분을 삭감하지 않는다. 초기 3인의 50% 집중은 외부 참여와 시장 공급 측면의 검토 과제로 공개하되, 권리 변경은 당사자 동의와 실행 가능성을 확인한다.

## 4. 개인별 해제 일정 — 기존 조건 유지

| 대상 | 개인 배분 (SHAH) | 조건 |
| --- | ---: | --- |
| 성재 | 166,666,667 | T12까지 0, T13~T36에 24회 월별 해제 |
| 동원 | 166,666,667 | T12까지 0, T13~T36에 24회 월별 해제 |
| 박원 | 166,666,666 | T0에 10% 자유, T1~T24에 나머지 90% 월별 해제 |

박원의 즉시 자유 물량은 **16,666,666.6 SHAH**, 제한 물량은 **149,999,999.4 SHAH**, 월 해제량은 **6,249,999.975 SHAH**다. 자유·해제 물량의 이전과 매도에 건별 추가 승인을 요구하지 않는 v0.5 설계를 유지한다. 가격·회수 가능 금액은 보장하지 않는다.

T0는 3인 합의와 실제 제한 물량 예치를 확인한 UTC 시각이며 아직 확정 증빙이 없다. TGE는 별도 최초 공개 유통일이다. 월말·윤년과 각 회차의 시각은 배포 전에 고정한다. 운영자의 첫 회차는 T13이며 T12 일괄 지급은 없다. 문서 개정일·새 기술 출시·PR 병합을 T0로 보거나 일정을 재시작하지 않는다.

decimals 9 기준 제한 물량의 최소 단위 정수를 A, 완료 회차를 k라 하면 누적 해제량은 `floor(A × k ÷ 24)`, 신규 청구 가능량은 누적량에서 기존 청구량을 뺀 값이다. 즉시 자유 물량은 A에서 제외하고 마지막 회차에 잔여 최소 단위까지 정산한다. 각 운영자의 월평균 근사값은 **6,944,444.458333333 SHAH**다. 실제 회차 계산은 정수 산식을 따른다.

| 구간 | 운영자 2인 신규 해제 | 투자자 신규 해제 | 초기 3인 누적 해제 |
| --- | ---: | ---: | ---: |
| T0 | 0 | 16,666,666.6 | 16,666,666.6 |
| T1~T12 | 0 | 74,999,999.7 | 91,666,666.3 |
| T13~T24 | 166,666,667 | 74,999,999.7 | 333,333,333 |
| T25~T36 | 166,666,667 | 0 | 500,000,000 |
| T36 이후 | 0 | 0 | 500,000,000 |

이 표는 예정 해제량이다. 실제 잠금·예치·청구·지갑 유입은 각각 증빙한다. 개인 지갑 전송만으로 잠금이 성립하지 않는다. 나머지 배정 50%의 승인 지급·LP 예치 상한을 추가해야 전체 공급 전망이 된다.

## 5. SHAH 사용처 — 서비스별 검증 후 도입

다음 항목은 사용처 후보이며 현재 제공되는 유료 기능·요금·확정 매출이 아니다. 보안 복구·긴급 중단·자산 확인 같은 필수 안전 절차는 SHAH 보유·신규 구매·추가 예치 여부로 제한하지 않는 것을 제안한다.

| 후보 | 지불 주체와 제공 가치 | SHAH의 역할 후보 | 도입 전 확인 |
| --- | --- | --- | --- |
| 선택형 운영 도구 | 팀·소규모 사업자의 관리형 알림, 보고서·증빙 관리 | 선택적 결제 수단 또는 예산 내 할인 | 작동하는 서비스, 유료 이용 의사, 원가·지원 부담 |
| 고객별 구축·연동 | 운영 도구 설치·맞춤 보고·유지보수 계약 | 계약 상대가 선택하는 결제 후보 | 계약·납품 범위, 수락 자산, 환불·지원 의무 |
| 검증된 기여 | 개발·문서·시험·보안 개선 성과 | 기존 목적 예산에서 지급하는 보상 | 사전 과제·수령자·한도·검수자·중복 심사 |
| 선택형 게임 콘텐츠 | 외형·한정 콘텐츠 등 이용 경험 | 선택형 소비 결제 후보 | 콘텐츠 완성, 소비 수요, 별도 게임 예산 |
| 커뮤니티 의견 수렴 | 기능 제안·우선순위 참여 | 참여 기준 후보 | 실명·다중 계정·이해상충 검토, 구속력 없는 제안 범위 |

현재 유료 서비스, 할인율, 토큰 보유 등급, 서비스 이용권, DAO 투표권을 부여하지 않는다. SHAH 수량으로 Treasury 출금·관리자 권한·복구 정족수를 결정하지 않는다. Guardian 역할이 Solana 검증자 지분이나 SHAH 스테이킹 수익으로 연결된다는 설계도 채택하지 않는다.

각 서비스는 다음의 출시 카드를 갖춘 후 별도 승인한다: 제공 기능, 고객, 대체 결제 수단, 기본 가격 기준, SHAH 결제·할인 방식, 가격 출처와 유효시간, 결제 실패·환불, 비용·지원 의무, 보상 예산과 시행일. 유효한 시장 가격·유동성 근거가 없으면 SHAH 환산 결제를 보류한다. Devnet 단위로 금전 요금을 청구하지 않는다.

## 6. 서비스 수익과 토큰 수요의 연결

유료 운영 도구와 구축·지원 계약을 우선 검증한다. 고객 문제 해결 → 계약·결제 → 서비스 제공 → 비용 정산과 재투자 흐름을 기록한다. 결제 자산과 매출 인식·원화 평가·세무 처리는 실제 출시 구조에 맞춰 검토한다.

SHAH 결제는 고객에게 선택지가 될 수 있으나, 서비스 매출이 토큰 보유자의 청구권이나 수익 배분으로 자동 이전되지는 않는다. 고정 수익·의무 배당·의무 바이백·자동 소각·가격 하한을 본안에 두지 않는다. 별도 보유 예치로 수익을 약속하는 기능은 본 개정 범위에 없다.

| 지표 | 기록 방식 | 해석 |
| --- | --- | --- |
| 서비스 결제 | 주문 ID별 자산·수량·원화 참고 평가·환불 | 실제 서비스 수요 확인 |
| SHAH 결제 선택률 | 서비스 주문 중 SHAH 사용 주문 비중 | 토큰 결제 선택의 유용성 확인 |
| 외부 취득 SHAH | 확인 가능한 외부 취득 근거가 있을 때만 별도 기록 | 기존 잔액 결제·보상 재사용과 구분 |
| 지급 보상 | 목적 예산·수령자·검수 결과·실제 지급 | 시장 공급 가능 물량으로 반영 |
| 재무 수취 SHAH | 서비스 결제 등 유입 사유와 잔고 | 사용 가능 현금과 별도 기록 |

SHAH 결제량 전부를 신규 매수 수요로 계산하지 않는다. 기존 보유분이나 보상분을 재사용할 수 있다. 재무 지갑으로 돌아온 SHAH도 재사용·매각될 수 있으므로 소각·영구 공급 감소로 표시하지 않는다. 내부 주소 이동과 반복 결제로 주문·수요를 부풀리지 않는다.

할인은 매출과 원가가 감당할 수 있는 승인 예산에서 설계한다. 매각이 필요한 SHAH 보상에 의존해 서비스 원가를 지급할 계획이면, 환전 가능성·가격 영향·현금 부족을 함께 점검한다. 기술이 출시되지 않거나 유료 수요가 없으면 토큰 수요 역시 검증되지 않은 상태로 공개한다.

## 7. 개발·보안 비용과 보상의 집행

개발·운영 100M의 세부 배분 비율은 아직 정하지 않는다. 실제 과제·현금 견적과 유지비를 확인한 뒤 월 예산을 정한다. 개발 구현, 독립 검토·감사, 인프라, 운영 지원을 장부에서 구분한다. 게임 보상 100M이나 유동성 150M을 개발비 부족을 이유로 자동 전용하지 않는다.

| 단계 | 필수 증빙 | 지급 조건 |
| --- | --- | --- |
| 과제 승인 | 목적, 기존 예산 항목, 지급 자산·한도, 납기, 수령자·이해상충 | 수행 전 승인 |
| 산출물 제출 | 코드 커밋·문서·시험 결과·재현 절차 | 제출만으로 지급 완료 처리하지 않음 |
| 검수 | 승인된 범위 충족, 실패·보안 이슈, 검수자 | 일반 지출·이해상충 규칙 적용 |
| 정산 | 계약·영수증·TXID 또는 지급 증빙, 중복 확인 | 실제 지급과 장부 대조 |

누적된 Draft PR 수나 자동 생성한 커밋 수만으로 기여 점수를 확정하지 않는다. 같은 변경의 부모·자식 PR, 재작성, 테스트 수 증가는 독립 성과로 중복 지급하지 않는다. 보안 취약점 보상은 대상 범위·한도·재현·공개 유예를 사전 공지하고, 제한된 예산과 검수에 따른다. 팀 내부 시험은 독립 외부 감사로 표시하지 않는다.

매월 신규 재량 집행은 승인된 목적·자산·수량 한도 내에서만 가능하다. 예산이 없으면 신규 재량 지급 한도는 0이다. 기존 계약상 의무는 별도 기록하고 임의 소멸시키지 않는다. 토큰 예산, 실제 지급, 유통 가능 증가량과 가용 현금을 각각 대조한다.

## 8. 게임·CHURU 경제의 분리

CHURU는 게임 내부 오프체인 포인트이며 SHAH·현금에 대한 고정 청구권을 주지 않는다. 일반 플레이는 SHAH 구매·지갑 연결 없이 가능하도록 설계한다. CHURU 지급·소모·회수는 게임 장부로 관리하고 SHAH 소각과 구분한다.

기존 게임 시범 SHAH 보상 조건을 유지한다: **운영 개시 후 첫 6개월, 월 최대 500,000 SHAH, 누적 최대 3,000,000 SHAH**, 개인 상한은 월 승인 예산의 2%, 미사용분은 다음 달 한도에 자동 가산하지 않는다. 개정일로 시범 기간을 재시작하지 않는다. 실제 운영 시작일은 별도 승인·공개한다.

월 승인 예산 B, 개인 검증 점수 s, 전체 점수 S에 대해 개인 지급량은 `min(B × s ÷ S, 0.02 × B)`를 최소 단위로 내림한다. S=0이면 지급하지 않고, 개인 상한 때문에 남은 물량은 재분배하지 않는다. 점수·다중 계정·부정 이용 심사·이의신청은 [v0.5 게임 정책](tokenomics-v0.5-ko.md)을 유지한다.

이 한도는 게임 시범 보상의 한도다. 기술 개발 보상에 새로운 월 500,000 한도를 자동 배정하는 규정이 아니다. 목적이 다른 보상은 해당 기존 배정과 별도 월 예산을 따르며 전체 공급 전망에는 함께 합산한다.

## 9. Treasury·보관 권한·거버넌스

Treasury는 공동 운영자금·준비금 전체이며 비상 예비금 5%와 구분한다. 현재 사용자가 확인한 운영 형태는 성재 관리 주소를 공동 Treasury와 성재 정책 승인자에 함께 사용하는 것이다. 실명 확인, 실제 독립 키 통제와 잔고 귀속은 별도 검증한다. 개인키·시드는 수집하지 않는다.

겸용 주소의 전체 잔고를 성재 개인 몫 또는 공동 운영자금으로 일괄 분류하지 않는다. 개인 배정, 공동 예산, 외부 출자·대여·지원금, 서비스 수입을 사유·거래별 보조 장부로 구분한다. 기존 보유분의 귀속은 계약·합의와 거래 증빙으로 확인한다. 증빙 없는 잔액은 미분류로 남겨 추가 지출 근거로 사용하지 않는다.

| 결정 | 동의 기준 | 추가 통제 |
| --- | --- | --- |
| 월 예산 | 기존 3인 전원 | 목적·자산·수량·수수료·기간 명시 |
| 예산 내 일반 지출 | 이해관계 없는 서로 다른 2인 | 동일 버전 승인·중복 지급 방지 |
| 본인·관련자 지급 | 이해관계자 제외 후 나머지 2인 | 관련자 신고·독립 검수 |
| 예산 밖 집행·예비금·목적·권한·공급 변경 | 3인 전원 동의 제안 유지 | 수혜자 권리 변경은 당사자 동의도 확인 |

예외 지출에서 이해상충 제외와 전원 동의를 동시에 충족할 수 없으면 집행을 보류하고 별도 정책 검토를 한다. 긴급 사유로 단독 승인·지출 분할을 허용하지 않는다. 토큰 보유량과 승인 투표 수는 별개이며 Treasury 관리 역할로 추가 표를 갖지 않는다.

main의 도구는 요청·버전·Ed25519 메시지 검증·로컬 원장과 내보내기를 구현했다. `policy_approved`는 정책 승인 완료이며 실제 출금·체인 확인·장부 정산 완료를 뜻하지 않는다. 실제 자금 보관이 단일 키로 통제된다면 그 키 보유자의 기술적 출금 가능성을 공개한다. 화면의 2인 승인 규정이 이를 차단한다고 발표하지 않는다.

온체인 다중서명 전환 시 프로그램·Vault·서명자·임계값·관리자 권한·전체 거래 명령·버전과 실제 실행을 검증한다. 불명확한 전송 결과는 먼저 체인과 TXID를 조회해 중복 지급을 막는다. 로컬 해시 연결은 외부 공증이나 관리자에 대한 변조 불가능성을 뜻하지 않는다. Guardian 연구는 배포·감사·자금 통제 증빙을 확보하기 전까지 기존 재무 권한을 대신하지 않는다.

## 10. 공급·유통·유동성

최초 유통량과 Mainnet Mint는 본안에서 확정하지 않는다. TGE 시점의 실제 LP 예치량, 이미 이전 가능한 개인 물량과 외부 지급 자유 물량을 중복 없이 합산한다. 공개할 비유통 지갑·제외 사유·기준 시각을 정하고, 단순 내부 이동을 신규 시장 공급으로 계산하지 않는다. 예정 해제·실제 청구·시장 매도를 구분한다.

18%나 7~12%를 일률 목표로 두지 않는다. LP 배정 150M은 전체 한도다. 실제 예치에는 상대 자산의 가용 금액, 풀 주소·네트워크·자산쌍·가격 조건, 수수료·가격 영향, LP 소유·인출·잠금 조건과 승인 증빙이 필요하다. 풀 화면·생성 코드만으로 실제 유동성 공급 완료를 공시하지 않는다. 예치 자산은 필수 운영 현금과 분리한다.

매월 다음 달의 개인 해제와 각 목적의 최대 신규 지급·예치량을 합산해 시장 공급 상한을 공개한다. 같은 토큰의 지급·결제·내부 회수를 중복 합산하지 않는다. 공개 후 공급 상한 확대에는 기존 v0.5의 전원 동의 및 시행 7일 전 공지 제안을 유지한다. 이미 자유로운 물량을 사후 잠금으로 바꾸지 않는다.

## 11. 총량·배분 재설계의 의사결정 기준

| 선택지 | 현재 판단 | 채택 전 필요한 자료 |
| --- | --- | --- |
| A. 10억과 현재 수량 유지 | **이번 개정의 기준안** | 실제 사용처·비용·지급·현금 자료 축적 |
| B. 기존 목적 예산 재편 | 검토 과제 | 미집행 잔액·기존 약정·새 목적·희석 및 공급 영향·관련 동의 |
| C. 추가 발행 | 이번 개정에서 제안 수량·일정 없음 | 기존 예산 부족 근거, B안 비교, 발행 한도·수혜자·기간·희석·권한·수혜자 동의 검토 |

시장에 다른 코인이 몇 개 발행했는지나 단위 가격이 작다는 이유만으로 총량을 바꾸지 않는다. 서비스 기능 증가만으로 토큰 추가 발행이 필요해지는 것도 아니다. 필요한 것은 검증된 서비스 수요, 실제 운영비와 보상 설계다.

Mint Authority가 남아 있으면 정책상 10억 기준과 기술적 발행 차단 상태를 구분한다. 권한을 None으로 폐기하면 해당 권한이 영구 제거되므로 실제 배포·운영 요구와 별도 동의를 확인한 뒤 실행한다. 본 문서는 폐기나 추가 발행을 승인하지 않는다. [Solana 권한 문서](https://solana.com/docs/tokens/basics/set-authority)

3인 배정 50%는 집중도·장기 기여자 유치·해제 후 시장 공급을 함께 검토한다. 배정 목적·수혜자·서명 권한은 별도 항목이다. 검토를 시작했다는 이유로 개인 수량을 자동 삭감하거나 늘리지 않는다.

## 12. 월간 지표와 스트레스 점검

| 영역 | 월간 보고 항목 |
| --- | --- |
| 기술 | 실제 배포 버전·실행 증빙·실패·복구 시험·미해결 보안 이슈 |
| 서비스 | 실제 유료 고객·제공 완료 주문·환불·재이용·지원 비용 |
| 토큰 사용 | SHAH 결제 주문·수량·기존 보유/보상 재사용 확인 범위 |
| 공급 | 발행·유통 산정·예정 해제·실제 청구·목적별 실제 지급·예치 |
| 재무 | 자산별 가용 잔액·미분류 잔액·약정 의무·개발/감사/운영 비용 |
| 승인 | 목적·자산·수량·이해상충·승인자·버전·실제 지급 증빙 |
| 게임 | 별도 DAU·재방문·CHURU 지급/소모·시범 보상·부정 이용 |

가격·거래량·PR 개수는 제품 이용과 영업 수익의 대체 지표로 사용하지 않는다. 데이터가 없으면 미확인으로 표시하고 추정치를 실적으로 채우지 않는다.

스트레스 점검은 (1) 유료 수요가 없는 경우, (2) SHAH 결제 전부가 기존 보상 재사용인 경우, (3) 보상과 해제 물량의 동시 매도, (4) 현금 비용이 계속되지만 토큰 환전이 어려운 경우, (5) 기술 장애·복구 지연을 포함한다. 가격 영향은 실제 풀 구조와 상대 자산으로 계산한다. 운영 현금 여력이 예상 순지출 3개월분 미만이면 신규 확장·보상 확대를 재검토하는 v0.5 기준을 유지한다. 순지출이 0 이하이면 잔액과 고정 의무를 직접 표시한다.

## 13. 채택과 후속 실행

1. 3인이 기존 수량·해제 조건 유지와 v0.6 추가 규정을 항목별로 검토하고 의결·시행일을 남긴다. 실제 계약상 권리도 별도 확인한다.
2. 서비스 후보 중 첫 검증 대상을 정하고 기능·비용·고객·가격·대체 결제·SHAH 필요성을 기록한다. 가격·할인율은 그 단계에서 정한다.
3. 기존 토큰 잔고의 개인/공동 귀속과 출자·대여·수입을 대조하고, 기술·보안 비용의 자산별 월 예산을 승인한다.
4. 변경이 채택되면 대시보드·승인 메시지·공시의 정책 버전을 전환한다. 기존 승인·원장·서명을 새 버전으로 임의 재해석하지 않는다.
5. Devnet 검증·독립 보안 검토·실행 증빙을 갖춘 기능만 제한 공개하고, 실제 토큰·권한 변경은 별도 거래와 동의를 확인한다.

미정 항목은 첫 유료 서비스, 가격·할인율, 세부 개발/감사 예산, 실제 운영 현금, T0·TGE, Mainnet·LP 배포값, 온체인 통제와 권한 상태다. 채택일·책임자·근거·미해결 사항을 [검토표](tokenomics-v0.6-review.md)에 기록한다. 3인 동의란은 서명이 확보되기 전까지 비워 둔다.

본안은 원금·고정 수익·상장·유동성·가격 유지·회사 지분·자동 수익배분을 보장하지 않는다. 유료 서비스·판매·현금성 보상은 실제 출시 방식에 맞는 법률·세무·이용자 보호 검토를 별도로 진행한다.
